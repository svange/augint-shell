`augint-shell` is a Python 3.12+ command-line tool (the `ai-shell` command) that launches AI coding tools (Claude Code, Codex, opencode) and local LLMs (Ollama, Open WebUI, Kokoro TTS, Speaches STT) in per-project Docker containers. It is built on [Click](https://click.palletsprojects.com/) for the CLI and the [Docker SDK for Python](https://docker-py.readthedocs.io/) to build and orchestrate those containers. As a library/CLI it runs no servers of its own: releases are published automatically to [PyPI](https://pypi.org/project/augint-shell/) (`augint-shell`) and [Docker Hub](https://hub.docker.com/r/svange/augint-shell) (`svange/augint-shell`).

## Release & Branch Model

`augint-shell` is a library/CLI: it has no staging or production servers. Instead of deploy environments, git refs map to publish targets, and releasing is fully automated -- there is no manual deploy step.

| Git ref | Pipeline runs | Publishes to |
|---|---|---|
| Feature branch -> PR to `main` | Code quality, security scans, license compliance, unit tests, build validation | Nothing (validation only) |
| Push / merge to `main` | All of the above, then [Python Semantic Release](https://python-semantic-release.readthedocs.io/) cuts a version when Conventional Commits warrant one | [PyPI](https://pypi.org/project/augint-shell/), [GitHub Releases](https://github.com/svange/augint-shell/releases) (standalone binaries), [Docker Hub](https://hub.docker.com/r/svange/augint-shell), and the [Pipeline Artifacts](#pipeline-artifacts) reports on GitHub Pages |

The single deploy environment is the GitHub Actions `pypi` environment (trusted publishing via OIDC -- no stored PyPI token). The Docker image also rebuilds when files under `docker/` change, independent of a version bump. Full pipeline: [`.github/workflows/publish.yaml`](.github/workflows/publish.yaml).

## What This Does

`ai-shell` is a Python CLI that stands up:

1. **Per-project dev containers** (`augint-shell-{project}-dev`) -- one per repo, runs Claude Code, Codex, opencode, or pi with your project mounted, SSH keys, AWS creds, and tool configs wired in. The image also carries `chezmoi`, so `chezmoi init --apply <your-dotfiles-repo>` inside a container gives it your shell and tool config.
2. **Host-level LLM stack** (shared singletons) -- Ollama, Open WebUI, Kokoro TTS, Speaches STT, a Pipecat voice agent, and n8n on a common Docker network. GPU auto-detected.

One command replaces the old Makefile + docker-compose.yml workflow.

## Getting Started

> This project uses AI-assisted development. You do not need to memorize
> git commands or CI configuration -- your AI agent handles that.

### Prerequisites

- Docker, or Podman with the `docker` CLI shim (`podman-docker`) and `DOCKER_HOST` pointing at its socket
- [uv](https://docs.astral.sh/uv/) (it installs its own Python; **not required** when using the standalone binary)
- (Optional) NVIDIA GPU + drivers for local LLM acceleration

### First-time setup

```bash
uv tool install augint-shell
# update later:  uv tool upgrade augint-shell
```

Do not install it with `pip` into a system Python. When that Python is removed, its `Scripts\ai-shell.exe` (or `bin/ai-shell`) stays behind, can stay first on `PATH`, and exits with no output.

#### Without Python or PyPI (standalone binary)

On systems that block Python package registries or do not allow `pip` / host Python installations, `ai-shell` is also distributed as a single self-contained executable that requires no root/admin privileges and no host Python:

1. **From [GitHub Releases](https://github.com/svange/augint-shell/releases):** download the binary for your platform (`ai-shell-linux-x86_64`, `ai-shell-macos-arm64`, or `ai-shell-windows-x86_64.exe`) and place it in a user directory on your `PATH` (such as `~/.local/bin/ai-shell` with `chmod +x`, or `%USERPROFILE%\.local\bin\ai-shell.exe` on Windows).
2. **Directly from the Docker image (Linux x86_64):** if your environment only allows pulling Docker images, extract the standalone Linux binary straight from `svange/augint-shell`:
   ```bash
   mkdir -p ~/.local/bin
   docker run --rm --entrypoint "" svange/augint-shell:latest cat /usr/local/bin/ai-shell > ~/.local/bin/ai-shell
   chmod +x ~/.local/bin/ai-shell
   ```
   To update later, pull the latest image (`docker pull svange/augint-shell:latest`) and re-run the command above.

### Running locally

```bash
# Launch Claude Code in the current project
ai-shell claude

# Launch with extra args
ai-shell claude -- --debug

# Set up local LLM stack (first time)
ai-shell llm setup

# Launch opencode with local LLM
ai-shell opencode
```

## Configuration

Optional `.ai-shell.yaml` in your project root (YAML default, TOML also accepted). Run `ai-shell init` for the full reference: every key with an example, all commented out, so the new file changes nothing until you uncomment a line. The same reference is at `~/.augint/.ai-shell.example.yaml`. A project file needs only the keys it changes; every other key comes from `~/.augint/.ai-shell.yaml`. To keep a project file out of git without editing `.gitignore`, add `.ai-shell.yaml` to `.git/info/exclude`.

```yaml
container:
  image: svange/augint-shell
  image_tag: latest
  extra_env:
    MY_VAR: value
  dev_ports: [3000, 4200, 5000, 5173, 5678, 8000, 8080, 8888]
  extra_ports: []

openai:
  profile: work  # resolves OPENAI_API_KEY_WORK from .env

claude:
  account: work  # resolves CLAUDE_CODE_OAUTH_TOKEN_WORK from .env, or the login profile
  chrome_proxy: ""  # host Chrome proxy: "vpn" (ai-shell's VPN container) or a --proxy-server value

vpn:
  country: United States  # gluetun SERVER_COUNTRIES; empty = any NordVPN server
  firewall: true          # gluetun's own firewall; ai-shell turns it off by itself where it cannot run
  proxy_port: 8888        # loopback port of the proxy Chrome uses

expo:
  auto: true  # start a detected Expo app automatically (--expo/--no-expo override)

llm:
  primary_chat_model: qwen3.5:27b
  secondary_chat_model: huihui_ai/qwen3.5-abliterated:27b
  primary_coding_model: qwen3-coder:30b-a3b-q4_K_M
  secondary_coding_model: huihui_ai/qwen3-coder-abliterated:30b-a3b-instruct-q4_K_M
  context_size: 32768
  ollama_port: 11434
  webui_port: 3000
  comfyui_port: 8188
  extra_models: []
```

Global config at `~/.augint/.ai-shell.yaml` (canonical), `~/.ai-shell.yaml` or `~/.config/ai-shell/config.yaml` also supported.

### Host and container package installs never collide

The container overlays named volumes on the project's `node_modules`, `vendor/` and the uv venv, so a Linux install never lands in the bind-mounted Windows checkout. Workspace packages declared in `pnpm-workspace.yaml` or `package.json` `workspaces` (any directory with a `package.json` that matches) are overlaid the same way automatically; without that, pnpm on Windows and pnpm in the container keep reinstalling over each other's workspace links. Add `container.node_modules_paths: [glob, ...]` for layouts those files do not describe.

### Launch-time caches

To keep tool launches fast, two preflight checks are cached on the host under `~/.cache/ai-shell/`:

| Cache | Default TTL | What it skips |
| --- | --- | --- |
| `image-pull` | 15 min | `docker pull` of the `latest` image to compare digests (network round-trip) |
| `bedrock-check` | 24 h | Bedrock `converse` preflight that verifies AWS auth + model access |

Tune via YAML or env vars:

```yaml
container:
  image_pull_cache_ttl: 900       # seconds (0 = always pull)
aws:
  bedrock_check_cache_ttl: 86400  # seconds (0 = always verify)
```

Equivalent env vars: `AI_SHELL_IMAGE_PULL_CACHE_TTL`, `AI_SHELL_BEDROCK_CHECK_CACHE_TTL`. Delete the corresponding file under `~/.cache/ai-shell/` to force a recheck on the next launch.

## Claude Code multi-account switching (`--account`)

`ai-shell claude` can use a different Claude account for each launch. An account has one of two credentials:

| Credential | Where it lives | Good for | Not for |
|---|---|---|---|
| **Token** from `claude setup-token` | `CLAUDE_CODE_OAUTH_TOKEN_<NAME>` in `~/.augint/.env` | Normal terminal sessions. Shares your `~/.claude` settings and history. | Remote Control. Claude Code rejects these tokens for it. |
| **Login profile** from `claude auth login` | `~/.augint/claude-accounts/<name>/` (that account's own `CLAUDE_CONFIG_DIR`) | Remote Control, and sessions that must keep that account's own settings and history. Created automatically on first use. | Nothing. It is just slower to set up (one browser login). |

```bash
# ~/.augint/.env  (token accounts)
CLAUDE_CODE_OAUTH_TOKEN_WORK=sk-ant-oat01-...
CLAUDE_CODE_OAUTH_TOKEN_CLIENT=sk-ant-oat01-...
```

```bash
ai-shell claude --account work          # token if defined, else the login profile (created on first use)
ai-shell claude --account mike --login  # create (or refresh) mike's login profile, then launch
ai-shell claude --account mike --rc     # Remote Control as mike (login profile; asks to log in on first use)
ai-shell claude --account               # list the accounts (no secrets are shown)
ai-shell claude --account default       # use the ~/.claude login
ai-shell claude                         # use the configured account, else the ~/.claude login
```

The account name is the variable suffix, case-insensitive. A `-` in the name maps to `_`, and the login profile directory uses `-`.

Set a default for a project in `.ai-shell.yaml` (`claude.account: work`) or with `AI_SHELL_CLAUDE_ACCOUNT=work`. Use `--account default` to override it for one launch.

Rules:

- The selected token is injected as `CLAUDE_CODE_OAUTH_TOKEN` for the Claude process only. The other `CLAUDE_CODE_OAUTH_TOKEN_*` values are never passed into containers.
- `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are removed from the Claude process, because Claude Code prefers them over the OAuth token. A login profile also removes `CLAUDE_CODE_OAUTH_TOKEN`, for the same reason.
- Any `--account <name>` without a token in `.env` automatically uses (and creates) the login profile `~/.augint/claude-accounts/<name>/`, prompting for login on first use. Combining `--account` with `--aws` stops the launch with an error.
- Token accounts share `~/.claude` (settings and history). `claude -c` can continue a conversation that started under a different token account. A login profile has its own settings, history and plugins.
- `--rc` and `--login` always use the login profile, even when a token exists. `~/.augint` is already bind-mounted, so no container recreation is needed, and the profile survives container recreation.

## Attaching to host Chrome (`--local-chrome`)

`ai-shell claude --local-chrome` bridges Claude inside the container to a real Chrome on your desktop via the Chrome DevTools Protocol (using `chrome-devtools-mcp`). Unblocks OAuth popups, CAPTCHA pages, and "click around in a logged-in site" tasks.

- Claude drives Chrome tabs on your desktop in real time.
- **Windows, macOS and Linux hosts.** Chrome is found at its usual install paths (Windows, macOS) or on `PATH` as `google-chrome` / `chromium` (Linux). Chrome binds its debug port to loopback and ignores any other address. On Docker Desktop that is enough; on a Linux host (Docker or podman) ai-shell starts a small relay (`python -m ai_shell.cdp_relay`, log in `~/.augint/chrome/`) that listens on the address the container resolves for `host.docker.internal`, forwards to Chrome on loopback, and answers only the host's own addresses, so nothing on the network can reach Chrome through it. podman needs the `docker` CLI shim (`podman-docker`) and 4.1+ for `host-gateway`. With `DOCKER_HOST` pointing at a Podman socket, ai-shell also sets `CONTAINER_HOST` to it, so the shim (which ignores `DOCKER_HOST`) runs `docker exec` through the same Podman service; run from the terminal's own cgroup, those execs fail with "OCI permission denied" when the service runs under systemd.
- **Separate Chrome profile per project** -- your normal browsing untouched, each repo keeps its own logged-in state.
- **Separate Chrome profile per account** -- with `--account NAME`, the window is keyed by the account instead of the project, so Mike's sessions share one logged-in Chrome across repos and never touch Adam's.
- Profiles live under `%LOCALAPPDATA%\Google\Chrome\ai-shell\<slug>` on Windows and `~/.config/google-chrome/ai-shell/<slug>` elsewhere (`account-<name>` for accounts). Each has its own debug port, so several can run at once.
- All traffic stays on `localhost`.
- **The MCP server is checked before Claude starts.** `chrome-devtools-mcp` is installed in the image (and installed on demand in an older container). At every launch ai-shell starts it once, makes it list Chrome's pages through the bridge, and only then hands it to Claude. A broken bridge fails the launch with the server's own output instead of showing up inside Claude as an MCP server that "failed to start" (which is what an `npx` fetch on a cold container used to do when it outlasted Claude Code's startup timeout).

Set `claude.local_chrome: true` (or `AI_SHELL_LOCAL_CHROME=1`) to persist.

### Google sign-in

Google refuses to sign in inside a browser that exposes a DevTools port ("This browser or app may not be secure"), and that is the Chrome `--local-chrome` opens. It is Google's rule for automated browsers, not an address problem, so a VPN alone does not change it. ai-shell works around it by itself:

- **The claude.ai sign-in** that `--rc` and `--login` run (once per account per machine) opens, with `--local-chrome`, in a window on the same profile directory but WITHOUT the DevTools port, through the configured proxy. You sign in there (Google SSO works), the browser shows a code, you type it at ai-shell's prompt, and ai-shell closes that window and opens the debug-port Chrome on the same profile, which keeps the session. A previous session's debug-port window on that profile is closed first; it is ai-shell's own.
- **A Google session for later browser tasks** (Gmail, GHL behind Google SSO) comes with that same sign-in when the account is a Google one. For any other site that refuses an automated browser, `ai-shell chrome --account mike <url>` opens the plain window by hand: sign in, close it, and the next `--local-chrome` launch reuses the session.

Without `--local-chrome`, the sign-in URL is printed and works in any browser on any device; only the code comes back.

### Chrome through a VPN or proxy (`chrome_proxy`)

On a host whose own address sites refuse (a cloud dev box, a datacenter), Chrome gets a proxy. `claude.chrome_proxy` (or `AI_SHELL_CHROME_PROXY`, `--chrome-proxy` on `claude` and `chrome`) is either:

- **`vpn`**: ai-shell's own VPN container. ai-shell runs [gluetun](https://github.com/qdm12/gluetun) (NordVPN over WireGuard) as a host-level singleton container, `augint-shell-vpn`, with an HTTP proxy on `127.0.0.1:8888`, starts it before the first window opens, waits until traffic flows through it, and points Chrome at it. Rootless Podman is enough: `NET_ADMIN` and `/dev/net/tun`, no root. An account that owns a NordVPN [dedicated IP](https://nordvpn.com/features/dedicated-ip/) gets it without being asked: the token also names the account's dedicated-IP server, and gluetun is pinned to that server. A shared NordVPN exit is a datacenter address that Google scores like the host's own; the dedicated IP is the one its owner already uses on a phone or laptop. Settings under `vpn:` (country, firewall, proxy port); a changed setting recreates the container, and the country filter is ignored while a server is pinned. When gluetun's firewall cannot run in the container runtime, ai-shell recreates the container once without it and remembers (`~/.augint/vpn/firewall-off`).
- **a Chrome `--proxy-server` value** (`http://host:port`, `socks5://host:port`) for a proxy you run yourself.

Only the browser is proxied. The dev container and Claude Code keep the machine's own route, which Anthropic accepts. A running Chrome keeps the proxy it was started with; ai-shell's sign-in flow closes and reopens its own windows, so this matters only for a window you keep open across a config change.

The VPN credential is one line in `~/.augint/.env`:

```bash
NORDVPN_TOKEN=<access token>   # Nord Account -> NordVPN -> Manual setup -> Access token
```

ai-shell trades the token once for the account's WireGuard key through NordVPN's API and caches the key under `~/.augint/vpn/` (mode 0600); the token can expire, the key does not. `NORDVPN_WIREGUARD_PRIVATE_KEY=...` works too. Without either, `ai-shell vpn up` asks for the token on the terminal; a `--local-chrome` launch asks as well.

The same token is used once to look up the account's dedicated-IP server; the answer (a hostname, or "none") is cached in `~/.augint/vpn/nordvpn-server`. `NORDVPN_SERVER=us2943` (or the full `us2943.nordvpn.com`) in `.env` pins another server, `NORDVPN_SERVER=any` forces a shared one, and `ai-shell vpn down` forgets the cached answer. `ai-shell vpn status` prints the pinned server and the exit address, which should be the dedicated IP.

```bash
ai-shell vpn up        # start it now and print the exit address
ai-shell vpn status    # container state and exit address
ai-shell vpn down      # stop and remove it (and forget the firewall fallback)
```

## Remote Control (`--rc`)

`ai-shell claude --rc` runs `claude remote-control` (server mode) inside the dev container, so the project can be driven from [claude.ai/code](https://claude.ai/code) or the Claude mobile app. The process stays in your terminal; `Ctrl+C` stops it.

```bash
ai-shell claude --rc                                # your own account, session named after the project
ai-shell claude --rc "Billing fix"                  # custom session name
ai-shell claude --account mike --rc                 # as mike (login profile)
ai-shell claude --account mike --rc --local-chrome  # ...and give the session Mike's Chrome window
```

What happens on `--account mike --rc`:

1. `~/.augint/claude-accounts/mike/` becomes the session's `CLAUDE_CONFIG_DIR`. Your own `~/.claude` is not touched. A new profile gets a `CLAUDE.md` that imports your `~/.claude/CLAUDE.md` (`@/root/.claude/CLAUDE.md`, through the bind mount), so your personal instructions apply in Mike's sessions too; edit or delete that file to give the account its own. Settings, plugins and `~/.claude/rules/` stay per profile.
2. If that profile has no login yet, `claude auth login` runs first, driven from the host: ai-shell opens the sign-in page in the Chrome window it just opened for `mike` (or prints the URL unwrapped when no Chrome is attached), you sign in as Mike, the browser shows a code, and you paste it at ai-shell's own prompt. The URL and the code never pass through the container TTY, which is what used to mangle them. This happens once per account per machine.
3. With `--local-chrome`, `chrome-devtools-mcp` is registered for this project in that profile (`claude mcp add-json --scope local`), because server mode does not accept `--mcp-config`.
4. The server starts with `--permission-mode bypassPermissions` (omit with `--safe`) and the name `<project> (mike)`. Open claude.ai/code signed in as Mike to find it.

Requirements and limits (from Claude Code, not ai-shell):

- The account needs a Pro, Max, Team or Enterprise plan. Team/Enterprise owners must enable Remote Control in admin settings, and a "Trusted Devices" policy means your device must be verified under that account.
- Remote Control refuses `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` and Bedrock. ai-shell strips the first three and rejects `--aws`.
- Stopping the server and running the same command again brings the previous sessions back (Claude Code keeps them for about four hours).

## Remote control with T3 Code (`--t3`)

[T3 Code](https://github.com/pingdotgg/t3code) is a desktop/web/mobile GUI for driving coding agents. Its server owns the workspace — it spawns the agent processes, reads git state and hosts terminals — so it has to run *where the project lives*, which for ai-shell is the per-project dev container. That is what `--t3` sets up:

```bash
ai-shell claude --t3        # Claude in this terminal + T3 Code server for the project
ai-shell codex --t3
ai-shell pi --t3
ai-shell opencode --t3
ai-shell shell --t3         # Just the server, no tool
```

Each run:

1. installs the `t3` CLI in the container if the image predates T3 support;
2. starts `t3 serve --host 0.0.0.0 --port 3773` detached, with the same environment your tools get;
3. registers the project (`t3 serve` deliberately does not auto-add its cwd, which is why an unprepared server shows an empty environment);
4. mints a pairing token and prints a pairing URL + QR pointing at **this machine's LAN address and the container's published host port**.

Scan the QR from the T3 Code phone app, or paste the URL into the desktop app. The server keeps running after the local tool exits — that is the point.

Port `3773` is part of the standard dev-port set, so every dev container publishes it on a stable per-project host port. Containers created before this feature don't have that mapping; `--t3` says so and the fix is `ai-shell manage clean`, then rerun.

### T3 Connect (outside your LAN)

LAN pairing needs the phone on the same network. For anywhere-access, link the container once — the credential lives in the project's `~/.t3` volume, so it survives container recreation:

```bash
ai-shell shell
t3 connect link --headless      # prints a URL, paste back the code
exit
ai-shell claude --t3            # serve now also brings up the managed tunnel
```

`--t3` reports T3 Connect status on every run.

### What `--t3` is and isn't

T3 Code runs its *own* agent processes; it does not mirror the Claude session in your terminal. Both live in the same container against the same project and the same `~/.claude` config, so a conversation started in one can be resumed in the other — but they are separate processes.

Each project gets its own T3 environment (its own `~/.t3` named volume: server database, paired devices, Connect credential). The host's own `~/.t3` is never bind-mounted, so a desktop T3 Code install and the container servers never share a database.

## ACP clients (JetBrains Air, Zed)

ACP (Agent Client Protocol) is how an editor drives an outside coding agent: JSON-RPC over the agent's stdin and stdout. `ai-shell acp <tool>` is an agent command for such a client. The editor runs on the host; the agent runs in the project's dev container, with the same tools, mounts and Claude login as `ai-shell claude`. Your Claude subscription works, because the container has your `~/.claude`.

Register it in the client. For the Air plugin in IntelliJ IDEA, edit `~/.jetbrains/acp.json` (on Windows `C:\Users\<you>\.jetbrains\acp.json`):

```json
{
  "agent_servers": {
    "Claude (ai-shell)": {
      "command": "ai-shell",
      "args": ["acp", "claude", "--local-chrome"],
      "use_idea_mcp": false,
      "use_custom_mcp": false
    },
    "Claude mike (ai-shell)": {
      "command": "ai-shell",
      "args": ["acp", "claude", "--account", "mike", "--local-chrome"],
      "use_idea_mcp": false,
      "use_custom_mcp": false
    },
    "Codex (ai-shell)": {
      "command": "ai-shell",
      "args": ["acp", "codex"],
      "use_idea_mcp": false,
      "use_custom_mcp": false
    }
  }
}
```

Use the full path to `ai-shell` if the editor does not find it on `PATH` (`where ai-shell` on Windows, `command -v ai-shell` elsewhere). Then pick the agent in the Air chat.

| Option (`acp claude`) | Same as |
|---|---|
| `--account NAME` | `ai-shell claude --account NAME`. An account with no token creates its login profile on demand and signs in through the editor (see [Sign-in](#sign-in)). |
| `--local-chrome` / `--no-local-chrome` | `ai-shell claude --local-chrome`. Without either flag, `claude.local_chrome` applies. A `chrome_proxy: vpn` that needs a token prompt fails; save the token in `~/.augint/.env` first. |

How it works:

- One entry serves every project. The editor names the project folder in each session (`session/new`), and the proxy starts or reuses that folder's dev container.
- ACP paths are absolute, and the container sees the project at `/root/projects/<name>`. The proxy swaps the project root in both directions, for plain paths and `file://` URIs.
- The agent stays in the container. The proxy turns off the client's file, terminal and terminal sign-in capabilities, so the agent never asks the editor to act on the host. It also drops the MCP servers the editor offers (for Air, `idea64.exe stdioMcpServer`): they are host programs. So the agent does not get the IDE's own tools; ai-shell's Chrome DevTools MCP is added instead when local Chrome is on.
- The editor sends `initialize` before it names a project, so a short `docker run` of the adapter in the image answers it.
- Adapters: `claude-agent-acp` and `codex-acp` (npm, in the image; installed on demand on older images), and `opencode acp`. The Claude adapter runs the image's Claude Code (`CLAUDE_CODE_EXECUTABLE`).
- stdout is the protocol. ai-shell's own messages go to stderr, which the editor writes to its log (IntelliJ: `idea.log`).

### Sign-in

A session asks for a sign-in only when the login is missing or expired. Otherwise it starts with no prompt.

- At each new session, the proxy runs `claude auth status` in the container. It answers ACP's "auth required" only when there is no login, or when the login ends in less than 10 minutes. A token account, an API key or Bedrock is never checked.
- The editor then shows **Sign in (NAME)**. It runs `ai-shell acp login --account NAME` in a terminal on the host. That is the same sign-in as `ai-shell claude --account NAME --login`: the account's Chrome window (with `--local-chrome`), and the code typed in the terminal. The editor then retries the session.
- `ai-shell acp login` does nothing when the login is still good; `--force` signs in anyway. It uses the dev container of the project that asked (saved in `~/.config/ai-shell/acp-login.json`), or `--project-dir`.
- The login is stored where `ai-shell claude` keeps it (`~/.claude`, or `~/.augint/claude-accounts/NAME`), so terminal and editor sessions share it.
- A login that expires during a session gets the same sign-in when the agent reports it.
- The editor shows this only if it runs terminal sign-ins (Air does). Other editors get the error text, with the command to run.

Air's `acp.json` has no icon setting for custom agents, so put the account in the agent's name.

Not supported yet: the `--aws` and `--env` flags (`claude.provider: aws` in config does apply), and folders outside the project (Air's extra roots are dropped).

## Expo apps (`--expo`)

Expo apps get their dev server started **inside the dev container**, with the tunnel URL printed as a QR code before the agent takes the terminal — so you scan once, up front, and the phone stays attached for the whole session.

```bash
ai-shell claude              # auto-detected: Expo app -> dev server starts too
ai-shell claude --expo       # force it (and fail loudly if it can't start)
ai-shell claude --no-expo    # skip it
```

```
Expo
  Project: my-app (/root/projects/my-app)
  Scan:    exp://Xf3k2a-anonymous-8081.exp.direct
  Metro:   http://localhost:14631 (this machine)
  Log:     docker exec augint-shell-my-app-dev tail -f /var/log/ai-shell/expo-start.log

  <QR code>
```

The server is detached and outlives the tool session. Re-running any command just re-prints the QR against the live server.

### No Expo account needed

`expo start --tunnel` does not require a login. The Expo CLI connects with **its own** ngrok token and names the tunnel `{randomness}-{username}-{port}.exp.direct`, falling back to `anonymous` when nobody is signed in. Logging in only matters for EAS (`build`, `update`, `submit`).

If you do want to be signed in, the practical options in a container are `npx expo login` (persisted in `~/.expo`, which is bind-mounted) or an `EXPO_TOKEN` **personal** access token. Browser SSO does not work in the container: it binds a callback listener on an ephemeral container port and shells out to a browser that isn't there. A **robot** `EXPO_TOKEN` is worse than none here — the Expo CLI refuses to open a tunnel for robot users, and ai-shell reports that specifically if it happens.

### Why tunnel, and not LAN

ngrok dials *outbound* from the container, so the phone reaches `https://<subdomain>.exp.direct` with no published port involved. LAN mode cannot work as-is: ai-shell hash-assigns dev ports into 10000-39999 rather than mapping them identity, so Metro would advertise its own `:8081` and the phone would find nothing there. Port 8081 is published anyway, so a host browser can reach Metro and `expo start --web`.

The QR is stable across restarts: Expo persists the tunnel's random segment in `.expo/settings.json` inside the project directory, which is bind-mounted.

### Detection

Auto-start requires *both* an `expo` dependency in `package.json` and an app config (`app.json` with an `expo` key, or `app.config.{ts,js,mjs,cjs,json}`). A dependency alone also describes Expo libraries and config plugins, which have nothing to serve. `--expo` needs only the dependency.

`ai-shell shell` never auto-starts Expo — it is the maintenance path, often where you go to *fix* an install — but `ai-shell shell --expo` works. Set `expo.auto: false` in `.ai-shell.yaml` (or `AI_SHELL_EXPO_AUTO=0`) to turn auto-detection off for a project.

Dependencies are checked *inside* the container, because `node_modules` is a container-local named volume: a host-side `npm install` is invisible there. If Expo isn't installed in the container, auto-detection says so and steps aside rather than triggering an install.

## OpenCode (Bedrock Mantle, Custom Endpoints & Subagent Routing)

`ai-shell opencode` (or `ai-shell --agent opencode` / `ai-shell --harness opencode`) launches OpenCode in the dev container with persistent configuration (`~/.config/opencode`) and state (`~/.local/share/opencode`), non-destructive `opencode.json` merging, and no Claude Code files (see [section 5](#5-no-claude-code-files-plugins-and-chrome)).

### 1. AWS Bedrock Mantle (Commercial & GovCloud)

OpenCode connects to AWS Bedrock's OpenAI-compatible Mantle endpoints with `@ai-sdk/openai-compatible` (Chat Completions). Mantle serves models on two routes, and a model sent to the wrong route is rejected ("isn't supported on this route"). So ai-shell writes two providers into `opencode.json` and puts each model on the provider that serves it:

| Provider | Base URL | Models |
| --- | --- | --- |
| `bedrock-mantle` | `https://bedrock-mantle.<region>.api.aws/v1` | `openai.gpt-oss-120b`, `openai.gpt-oss-20b`, and other non-GPT models |
| `bedrock-mantle-openai` | `https://bedrock-mantle.<region>.api.aws/openai/v1` | `openai.gpt-5.6-terra`, `openai.gpt-5.6-luna`, `openai.gpt-5.4` |
| `bedrock-runtime` | `https://bedrock-runtime.<region>.amazonaws.com/openai/v1` | `xai.grok-4.7`, `xai.grok-4.6`, and any inference profile ID (`us.`, `us-gov.`, `global.`) |

A model given as `bedrock-mantle/openai.gpt-5.4` (or unqualified) is moved to the provider that serves it. Grok goes to `bedrock-runtime` with the Region's inference profile prefix added: `xai.grok-4.7` becomes `us-gov.xai.grok-4.7` in GovCloud and `us.xai.grok-4.7` elsewhere. Grok 4.7 is not on Mantle, and Grok 4.6 is on Mantle in us-gov-east-1 only. Mantle model IDs have no `-1:0` suffix; that suffix is the `bedrock-runtime` form. To list the inference profile IDs your account can use: `aws bedrock list-inference-profiles --query "inferenceProfileSummaries[].inferenceProfileId"`.

- **Commercial AWS** (`--aws-partition commercial`, default region `us-east-1`).
- **AWS GovCloud** (`--aws-partition govcloud`, default region `us-gov-west-1`).
- **Region**: `--aws-region`, then `opencode.aws_region` (`AI_SHELL_OPENCODE_AWS_REGION`). These must match the partition. Without them, OpenCode uses `aws.bedrock_region` (or `aws.region` when no partition is set) only when that region is in the partition, so a global `us-east-1` default for Claude does not break a GovCloud OpenCode. `opencode.aws_region` does not change Claude's Bedrock region.
- **Authentication**:
  - If `AWS_BEARER_TOKEN_BEDROCK` (or `BEDROCK_API_KEY`) is set on the host or in `~/.augint/.env`, it is forwarded into the container and referenced via `{env:AWS_BEARER_TOKEN_BEDROCK}` in `opencode.json`.
  - Otherwise, `ai-shell` makes a short-term Bedrock API key from your AWS profile (`--aws-profile` / `--profile`, or `opencode.aws_profile`) before it starts OpenCode. The key is the same one `aws-bedrock-token-generator` makes. It lasts 12 hours, or less when the SSO session ends sooner. Run `aws sso login --profile <profile>` first. Disable with `--no-generate-token`.
  - The profile needs `bedrock:CallWithBearerToken`, `bedrock-mantle:CallWithBearerToken`, `bedrock-mantle:ListModels` and `bedrock-mantle:CreateInference` for Mantle, and `bedrock:InvokeModel` on the inference profile and its models for Grok.
- **Default Mantle agent models**:
  - Commercial AWS: primary agents (`plan`, `build`) `bedrock-mantle-openai/openai.gpt-5.6-terra`; subagents (`explore`, `general`) and `small_model` `bedrock-mantle-openai/openai.gpt-5.6-luna`.
  - AWS GovCloud: `bedrock-mantle/openai.gpt-oss-120b` for all of them. On 2026-11-19 a standalone GovCloud account got "not available for this account" for GPT-5.6 Terra, Luna and GPT-5.4, and Grok on that account had a small daily token quota ("Too many tokens per day"). Set `model` and `subagent_model` when your account has access to more.
- **Model limits**: every Bedrock model in `opencode.json` gets a `limit` (context and output tokens, from the Bedrock model cards; 128000/16384 when no figure is published). Without one, OpenCode reads any failed request as a context overflow and the real error is hidden.
- **Only GovCloud providers in GovCloud**: a GovCloud config sets `enabled_providers` to the providers ai-shell writes (the three Bedrock providers and your `endpoints`). It also adds `amazon-bedrock` (OpenCode's built-in Bedrock provider, which lists Anthropic models) and `opencode` (OpenCode's hosted models, outside AWS) to `disabled_providers`; your own entries in that list are kept.

```bash
# Commercial AWS (defaults to us-east-1) using an AWS SSO profile
ai-shell opencode --aws --aws-profile my-bedrock-sso

# AWS GovCloud (defaults to us-gov-west-1) using a pre-set bearer token
export AWS_BEARER_TOKEN_BEDROCK="bedrock-api-key-..."
ai-shell opencode --aws --aws-partition govcloud

# AWS GovCloud with a key made from an SSO profile
aws sso login --profile ai-gov
ai-shell opencode --aws --aws-partition govcloud --aws-profile ai-gov
```

A standalone GovCloud account with access to GPT-5.6 Terra (for planning and building) and GPT-5.6 Luna (for subagents), and an optional own model on a GPU instance that you reach through a Session Manager port forward on host port 8000. Put this in `~/.augint/.ai-shell.yaml`:

```yaml
opencode:
  provider: bedrock-mantle
  aws_partition: govcloud
  aws_profile: ai-gov
  model: openai.gpt-5.6-terra     # or xai.grok-4.7; without these two lines: openai.gpt-oss-120b
  subagent_model: openai.gpt-5.6-luna
  endpoints:
    govcloud-gpu:
      base_url: http://host.docker.internal:8000/v1
      models:
        - MODEL_ID_SERVED_BY_VLLM
```

To check the key and the model IDs your account can use:

```bash
curl -H "Authorization: Bearer $AWS_BEARER_TOKEN_BEDROCK" \
  https://bedrock-mantle.us-gov-west-1.api.aws/v1/models
```

ai-shell merges into `~/.config/opencode/opencode.json` and keeps keys it does not set. To stop OpenCode from sharing sessions, add `"share": "disabled"` there.

### 2. Custom OpenAI-Compatible Endpoints (vLLM / SGLang)

Point OpenCode at one or more self-hosted OpenAI-compatible servers via CLI flags, environment variables, or `.ai-shell.yaml` without hand-editing `opencode.json`:

```bash
# Single custom vLLM server via dedicated flags
export VLLM_API_KEY="token-abc"
ai-shell opencode \
  --custom-name vllm \
  --custom-url http://host.docker.internal:8000/v1 \
  --custom-key-env VLLM_API_KEY \
  --custom-model Qwen/Qwen3-Coder-30B-A3B-Instruct

# One or more custom endpoints via repeatable --endpoint specs
ai-shell opencode \
  --endpoint "vllm=http://gpu-box:8000/v1,model=Qwen/Qwen3-Coder-30B-A3B-Instruct,api_key_env=VLLM_API_KEY" \
  --endpoint "sglang=http://fast-box:30000/v1,model=openai/gpt-oss-120b"
```

### 3. Splitting Primary (`plan`, `build`) vs. Subagent (`explore`, `general`) Models

Route primary reasoning/coding agents (`plan`, `build`) to a frontier model on Bedrock Mantle while offloading fast read-only/worker subagents (`explore`, `general`) to a secondary model or custom vLLM endpoint:

```bash
# Bedrock Mantle primary + Bedrock Mantle fast subagent
ai-shell opencode --aws \
  --aws-partition govcloud \
  --aws-profile gov-sso \
  --model bedrock-mantle-openai/openai.gpt-5.6-terra \
  --subagent-model bedrock-mantle-openai/openai.gpt-5.6-luna

# Grok 4.7 primary (bedrock-runtime, inference profile added for the Region)
ai-shell opencode --aws \
  --aws-partition govcloud \
  --aws-profile gov-sso \
  --model xai.grok-4.7

# Bedrock Mantle primary (plan, build) + self-hosted vLLM subagent (explore, general)
ai-shell opencode --aws \
  --aws-partition govcloud \
  --aws-profile gov-sso \
  --endpoint "vllm=http://gpu-box:8000/v1,model=Qwen/Qwen3-Coder-30B-A3B-Instruct,api_key_env=VLLM_API_KEY" \
  --model bedrock-mantle-openai/openai.gpt-5.4 \
  --subagent-model vllm/Qwen/Qwen3-Coder-30B-A3B-Instruct
```

Or persist the setup in `.ai-shell.yaml` or `~/.augint/.ai-shell.yaml`:

```yaml
opencode:
  provider: bedrock-mantle
  aws_partition: govcloud
  aws_region: us-gov-west-1
  aws_profile: gov-sso
  model: bedrock-mantle-openai/openai.gpt-5.4
  subagent_model: vllm/Qwen/Qwen3-Coder-30B-A3B-Instruct
  endpoints:
    vllm:
```

### 4. Browser UI, Headless Server & Status

```bash
ai-shell opencode --web                # Launches web UI, opens browser
ai-shell opencode --web --port 8080    # Custom port
ai-shell opencode serve                # Start headless server in container
ai-shell opencode serve --open         # Auto-open browser after starting
ai-shell opencode attach               # Attach a TUI to a running opencode server
ai-shell opencode status               # Show server URL, mDNS name, terminal count
```

mDNS is enabled by default — the server is discoverable on your LAN as `<project>.local`. CORS is set to `*` for cross-device access (phone, tablet).

`serve` waits up to 30 seconds for the server to answer. The server's output goes to `/tmp/opencode-serve.log` in the dev container. When the server exits at start, `serve` prints the end of that log and exits with an error.

The web UI and the server always ask for a password, because they listen on every host interface. The browser opens already signed in: the link that `opencode web` prints, `serve --open` and `opencode remote` carry the user and password in OpenCode's `auth_token` query parameter, and the web app removes it from the address bar. A browser opened on the plain address asks for user `opencode` and the password. By default, ai-shell makes the password on first use and keeps it in `~/.augint/opencode/server-password` (mode 600). `ai-shell opencode attach` sends it too. To use your own, set `OPENCODE_SERVER_PASSWORD` (and optionally `OPENCODE_SERVER_USERNAME`) in `~/.augint/.env` or the project `.env`:

```bash
# .env
OPENCODE_SERVER_PASSWORD=mysecret
OPENCODE_SERVER_USERNAME=admin
```

### 5. No Claude Code files, plugins and Chrome

**Claude Code files are off.** OpenCode reads Claude Code files by default. ai-shell turns that off for every launch (`OPENCODE_DISABLE_CLAUDE_CODE=1`, `OPENCODE_DISABLE_EXTERNAL_SKILLS=1`). OpenCode then does not read:

- `~/.claude/CLAUDE.md`, or `CLAUDE.md` in the project or a parent folder
- skills in `~/.claude/skills`, `~/.agents/skills`, or a project's `.claude/` and `.agents/` folders

It still reads `AGENTS.md` (project and parents), `CONTEXT.md`, `~/.config/opencode/AGENTS.md`, and skills in `~/.config/opencode/skills` and `.opencode/skills`. Put your own rules in `~/.config/opencode/AGENTS.md`. Run `/init` in OpenCode to write a project `AGENTS.md`.

Older ai-shell versions linked `~/.config/opencode/skills` to `~/.agents/skills` or `~/.claude/skills`, and `.opencode/skills` to `../.agents/skills`. ai-shell removes those links at launch. It removes only a link with one of those targets.

ai-shell writes nothing into the project for OpenCode. The container's own `/root/projects/AGENTS.md` (environment facts) is outside the bind mount. `ai-shell init` writes `.ai-shell.yaml` into the current folder. That reference names every section, `claude:` too, so in a repository that must not mention Claude, write only the keys you change (for example `opencode: {model: openai.gpt-5.4}`) and add the file to `.git/info/exclude`. To try a model for one session, use `--model` or `AI_SHELL_OPENCODE_MODEL`.

To read Claude Code files again: `claude_compat: true` (or `AI_SHELL_OPENCODE_CLAUDE_COMPAT=1`).

**Plugins and instructions.** Every launch adds these, in `OPENCODE_CONFIG_CONTENT` (no file is written; your own `plugin` and `instructions` entries stay):

| Entry | What it does |
| --- | --- |
| `@plannotator/opencode@0.28.67` | Plan review in a browser. The `plan` agent calls `submit_plan`. ai-shell prints the review URL at launch (container port 19432). |
| `opencode-pty@0.4.0` | Background and interactive terminals for the agent: dev servers, watch modes, REPLs. |
| [`opencode-shell-strategy`](https://github.com/JRedeker/opencode-shell-strategy) | Instructions for non-interactive shell commands (`-y` flags, no pagers or editors). Pinned to a commit. |

Versions are pinned. Set your own lists to change them; `[]` turns them off.

**Chrome.** `ai-shell opencode --local-chrome` (or `local_chrome: true`) attaches `chrome-devtools-mcp` to a project-scoped Chrome on your desktop, the same bridge as [`ai-shell claude --local-chrome`](#attaching-to-host-chrome---local-chrome). OpenCode gets the `chrome-devtools` MCP server: it can open pages, click, read the console and network requests, and take screenshots. `claude.chrome_proxy` (`AI_SHELL_CHROME_PROXY`) applies to this Chrome too: with `vpn`, only the browser goes through ai-shell's VPN container, and OpenCode and its model calls keep the host's address.

```yaml
opencode:
  claude_compat: false        # default
  local_chrome: true
  plugins:
    - "@plannotator/opencode@0.28.67"
    - "opencode-pty@0.4.0"
  instructions:
    - "https://raw.githubusercontent.com/JRedeker/opencode-shell-strategy/1303f24df1649202834e052f1d66560ed186e413/shell_strategy.md"
```

### 6. OpenCode on a remote box (SSM)

`ai-shell opencode remote` opens OpenCode that runs on an EC2 box, from this computer. The box needs ai-shell, Docker and the SSM agent, and the project in `<projects_dir>/<project>`. Nothing on the box listens to the network: the command uses SSM Run Command and an SSM port-forwarding session. This computer needs the AWS CLI v2 and the [Session Manager plugin](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html).

```yaml
# ~/.augint/.ai-shell.yaml
opencode:
  remote:
    instance: my-opencode-box      # instance id (i-...) or its Name tag
    aws_profile: my-gov-profile
    aws_region: us-gov-west-1
    user: dev                      # default dev
    projects_dir: ~/projects       # default ~/projects
    folder: projects               # optional: always this folder, not this folder's name
    start_command: ai-shell opencode serve   # default; runs as user in the project, {project} = folder
```

```bash
cd ~/projects/navy
ai-shell opencode remote           # project = this folder's name; or: ai-shell opencode remote navy
```

The command:

1. signs in with `aws sso login` when the profile's session has ended,
2. starts the box when it is stopped and waits until SSM reaches it,
3. runs `start_command` when the project's server does not answer, and waits until it does,
4. prints the user (`opencode`) and the password from the box,
5. forwards the server port to `localhost` and opens the browser, signed in with the password (`--no-browser`, `--local-port`).

Ctrl+C ends the tunnel. `--instance` overrides `opencode.remote.instance` for one run.

## EC2 instances (`ai-shell ec2`)

`ai-shell ec2` finds an instance in any of your AWS profiles, starts it, connects to it and stops it. It uses the AWS CLI v2 and the profiles you already have; it has no config of its own.

```bash
ai-shell ec2 ls                          # every profile in ~/.aws/config
ai-shell ec2 ls --profile client-a       # one profile (repeatable); signs in when needed
ai-shell ec2 start web                   # start a stopped instance and wait until it runs (--no-wait)
ai-shell ec2 connect                     # pick from a numbered list; a tunnel to 22 (3389 on Windows)
ai-shell ec2 connect web --ssh           # by Name tag or instance id
ai-shell ec2 connect i-0abc... --rdp     # opens mstsc, the macOS RDP app, xfreerdp or Remmina
ai-shell ec2 connect web --shell         # an SSM shell, no key needed; else --ssh
ai-shell ec2 connect web --port 8080     # a tunnel to any port
ai-shell ec2 stop web
```

- **Listing.** All profiles are read at the same time. A profile whose SSO session has ended shows as `signed out` with the `aws sso login` command to run; no browser opens. `--region` sets the region for every profile, `--all-regions` reads every enabled region. A profile that asks for input (an MFA code) fails at once instead of waiting.
- **Starting.** `ai-shell ec2 start` starts a stopped instance and waits until it runs (`--no-wait` returns immediately). When `connect` targets an instance that is not running, it asks whether to start it (`--start` and `--no-start` answer before). When `connect` started the instance, it asks at the end whether to stop it again (`--stop` and `--no-stop` answer before).
- **Getting in.** `connect` tries these one at a time, each only when it can work, and names the reason for each one that failed:
  1. SSM port forwarding: the instance is registered with SSM and this computer has the [Session Manager plugin](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-install-plugin.html).
  2. An EC2 Instance Connect Endpoint in the instance's VPC (ports 22 and 3389 only; AWS CLI 2.12 or later).
  3. The instance's public IP, then its private IP (for a VPN or a computer in the VPC).
- **Signing in with SSH.** The user comes from the image name (`ubuntu`, `admin` on Debian, else `ec2-user`; `--user`). The key is `--key`, else the instance's key pair file in `~/.ssh` (`<name>` or `<name>.pem`), else a temporary key sent with EC2 Instance Connect (valid for 60 seconds), else your SSH agent.
- **RDP.** With the key pair file, `--rdp` also prints the Windows Administrator password.
- **No changes to the account.** `ai-shell ec2` never adds a security group rule, changes IAM or installs an agent to get in. It writes only start, stop and the temporary EC2 Instance Connect key.
